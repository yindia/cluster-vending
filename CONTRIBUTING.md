# Contributing to cluster-vending

Thanks for working on cluster-vending. This page covers how the repository is
laid out, the checks every change must pass, and the rules that keep the
platform safe to change: generated code, render versions, the catalog and
proposals.

## Set up

Follow [docs/local-development.md](docs/local-development.md). It covers the
toolchain, a kind management cluster with Crossplane, an AWS account (your own
keys or assumed roles), and running the controller, API server, live reader and
console. `make help` lists every target.

## Where things live

| Path | What it is |
|---|---|
| `cmd/` | The cobra commands of the one binary: `serve`, `controller`, `live`, and the CLI. Keep them thin; logic and its tests belong in `pkg/`. |
| `idl/cloud/v1/` | The public API (`cloud.v1`, protobuf + Connect). Generated into `pkg/gen` and `ui/src/gen`. |
| `api/v1alpha1/` | The custom resources the platform stores state in (there is no database). Generated CRDs in `config/crd`. |
| `pkg/server/` | The API server: validation, plans, the store. It holds no AWS or workload-cluster credentials. |
| `pkg/reconcile/` | The controller's reconcilers: accounts, networks, clusters, components, upgrades, deletion. |
| `pkg/crossplane/` | Renders Crossplane managed resources and Helm releases from a plan. Pure functions; `RenderVersion` lives here. |
| `pkg/catalog/` | The component catalog: `definitions/*.yaml` and `release.yaml`, embedded in the binary. |
| `pkg/crossplane/aws/addons.yaml` | The EKS add-ons the platform knows and how it places them. |
| `pkg/cloudformation/` | The IAM role templates (tenant and management accounts), generated by `scripts/`. |
| `pkg/rollout/`, `pkg/upgrade/` | Channels, tiers, soak, gates: when a change may reach a cluster. |
| `charts/cluster-vending/` | The Helm chart that deploys the platform. |
| `config/` | Kustomize manifests (CRDs, RBAC, deployments, samples). |
| `ui/` | The tenant console (Next.js). See [ui/README.md](ui/README.md). |
| `docs/` | [architecture.md](docs/architecture.md) (how it works) and [proposals/](docs/proposals). |

## Before every commit

```sh
make check        # buf format/lint, golangci-lint, go vet, all Go tests with -race (~10 min)
```

For a UI change also run, in `ui/`:

```sh
npx tsc --noEmit -p .   # types
npx eslint <changed files>
npm test                # unit tests
npx playwright test tests/browser/<spec>.spec.ts   # with the console running on :3000
```

`make check` is what CI runs. A change that doesn't pass it doesn't go in. One
known exception: `pkg/live` `TestLoadSyntheticFleet` can miss its time limit on
a busy machine. Rerun it alone before treating it as a failure.

## How we write code

- **Tests first.** Write the failing test, see it fail, then make it pass. A bug
  fix comes with the test that would have caught it. Name tests after the
  behaviour they pin, as a sentence: `TestCreateOnAnExtendedMinor`,
  `TestBackoffPauseKeepsTheRememberedFailure`.
- **Small units.** Functions under ~50 lines, files under 800, no nesting past
  four levels. Split a file before it grows past the limit.
- **No silent failures.** Return errors with context (`fmt.Errorf("read node
  group %s: %w", name, err)`), and say in status what a person must do.
  Messages are full sentences that name the object, the cause and the fix.
- **Data, not code.** A new platform component is a definition file and a
  release pin, not Go. An EKS add-on is an entry in `addons.yaml`. Special
  behaviour comes from declared roles (`spec.role`), never from a component's
  name. If a change needs a name check in Go, it probably needs a field.
- **The management cluster is the source of truth.** State lives in custom
  resources. The API server never holds workload-cluster or AWS credentials;
  only the controller (and, read-only, the live reader) does.

## Generated files

Never edit generated output by hand. Change the source and regenerate:

| You changed | Run | Regenerates |
|---|---|---|
| `idl/**/*.proto` | `make generate` | `pkg/gen`, `ui/src/gen` |
| `api/v1alpha1/*.go` | `make controller-apis` | deepcopy, `config/crd`, RBAC |
| `scripts/*.py` (role templates) | `make cf-generate cf-lint` | `pkg/cloudformation/templates` |
| `config/rbac` | `make helm-sync` | the chart's RBAC copies |
| repository interfaces | `make mocks` | `pkg/database/repository/mock` |

API changes must pass `buf breaking`. Removed proto fields reserve their number
and name.

## Changes that reach running clusters

These rules exist because the platform changes real infrastructure on many
clusters:

- **RenderVersion.** If a renderer's output changes for an unchanged plan (an
  add-on's values, a node group, a Helm release's spec), bump `RenderVersion`
  in `pkg/crossplane/aws/aws.go` with a history entry, and update
  `config/samples/cloud_v1alpha1_release.yaml`. Without the bump, running
  clusters never receive the change. The add-on golden test fails when you
  forget.
- **Catalog changes** (a definition's values, chart, `requires`) roll out to
  clusters through the channel's tiers, not at once. Test them as such.
- **Versions** live only in `pkg/catalog/release.yaml`. Nothing else names a
  chart or Kubernetes version.
- **Upgrades** are automatic and gated (channels, tiers, maintenance windows,
  freezes). Extended-support minors (on no channel) run with Manual upgrades
  only. Don't add opt-out flags; add a gate.
- **Deletion** must leave nothing in the cloud. Change the deletion stages with
  a test of the full order.

## Proposals

Design changes that cross components, change the API or the data model, or
change how clusters are upgraded or deleted, start as a proposal in
[docs/proposals/](docs/proposals): `PROP-NN-short-name.md`, following the
existing ones (summary, problems today, goals and non-goals, design,
alternatives, rollout plan, open questions). Implement after it's agreed, and
mark its phases done as they land.

## Commits

One logical change per commit, in the form:

```
<type>: <what changed, as a sentence about behaviour>

<why: the problem, what the change does, anything a reviewer must know>
```

Types: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `perf`, `ci`. Add
`!` for a breaking API or behaviour change (`feat!: ...`). Describe the
behaviour, not the edit: `fix: a takeover of an import not observed yet says to
wait and retry`, not `fix: update takeover.go`.

Don't commit secrets, local settings (`hack/config.mine.yaml`), or anything
under `bin/`. AWS keys are never a flag or a file.

## Docs

Update [docs/architecture.md](docs/architecture.md) in the same commit as the
behaviour it describes, and [docs/local-development.md](docs/local-development.md)
when setup or troubleshooting changes. The examples under `examples/` must stay
valid: tests read them.
